# Auditoria 100/100 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Levar o site reservemkt.com.br de 67/100 para o mais próximo possível de 100/100 em Desempenho (mobile/desktop), reduzindo código morto e texto com marcas de IA, sem quebrar nenhuma página em produção.

**Architecture:** Next.js 15 App Router, TypeScript, Tailwind v4 + styled-components. O trabalho é dividido em 4 frentes independentes e sequenciáveis: (1) ganhos rápidos de performance sem mudar arquitetura, (2) remoção de código/dependências mortas, (3) conversão da home para Server Components (a maior alavanca, e a de maior risco), (4) revisão de texto (travessões). Cada tarefa termina com `npm run build` limpo e, quando aplicável, checagem manual no navegador.

**Tech Stack:** Next.js 15, React 19, TypeScript, Tailwind CSS v4, styled-components 6.

## Global Constraints

- Nenhuma mudança de performance entra sem `npm run build && npm run start` + Lighthouse local (mobile, aba anônima, 3 rodadas, mediana) antes/depois — regra de ouro do documento de auditoria.
- Não usar `git commit` automaticamente — o usuário controla quando commitar (ver memória do projeto).
- Não remover nada sem confirmar via `grep -r` que não há import ativo.
- `npm run lint` deve passar sem novos erros após cada tarefa.
- Preservar todo o comportamento visual/funcional existente — isso é uma auditoria de performance e limpeza, não um redesign.

### Task 2: Separar metadados do conteúdo em `blog-posts.ts`

- Modify: `src/data/blog-posts.ts`

**Interfaces:**
- Produces: `src/data/blog-meta.ts` exporta `interface BlogPostMeta` (todos os campos de `BlogPost` exceto `content`) e `export const blogPostsMeta: BlogPostMeta[]`.
- Consumes: `src/data/blog-posts.ts` continua exportando `interface BlogPost` (com `content`) e `export const blogPosts: BlogPost[]`, usado só por `/blog/[slug]`.

- [ ] **Step 1: Ler a lista completa de campos usados por `BlogPreview` e `BlogPageContent`**

Run: `grep -n "post\." "src/app/(public)/home/_components/BlogPreview/index.tsx" "src/app/(public)/blog/_components/BlogPageContent.tsx"`

Confirmar que nenhum dos dois usa `post.content` (apenas título, excerpt, slug, categoria, capa, data, `featured`, `readTime`). Se algum usar `content`, ele fica de fora da extração até ser corrigido separadamente.

- [ ] **Step 2: Criar `src/data/blog-meta.ts` gerando os metadados a partir de `blog-posts.ts`**

```ts
import { blogPosts } from "./blog-posts";

export interface BlogPostMeta {
  slug: string;
  title: string;
  excerpt: string;
  category: string;
  keywords: string[];
  readTime: number;
  publishedAt: string;
  featured: boolean;
  coverImage: string;
  coverAlt: string;
}

export const blogPostsMeta: BlogPostMeta[] = blogPosts.map(
  ({ content: _content, ...meta }) => meta
);
```

Isso é um passo intermediário seguro (não quebra nada, ainda importa `blog-posts.ts` inteiro). O Step 3 inverte a dependência para o ganho de bundle real.

- [ ] **Step 3: Build e checagem — versão intermediária funciona**

Run: `npm run build`
Expected: build sem erros (ainda sem ganho de bundle, só valida a extração de tipos).

- [ ] **Step 4: Trocar `BlogPreview` e `BlogPageContent` para importar de `blog-meta.ts`**

Em `src/app/(public)/home/_components/BlogPreview/index.tsx` e `src/app/(public)/blog/_components/BlogPageContent.tsx`, trocar:

```ts
import { blogPosts } from "@/data/blog-posts";
```

por:

```ts
import { blogPostsMeta as blogPosts } from "@/data/blog-meta";
```

(mantém o nome local `blogPosts` para minimizar o diff nesses arquivos — só troca a fonte).

- [ ] **Step 5: Trocar `src/app/sitemap.ts` para usar os metadados**

Run: `grep -n "blog-posts" src/app/sitemap.ts` para localizar o import e o uso (provavelmente só `slug` e `publishedAt`). Trocar o import para `blog-meta.ts` do mesmo jeito do Step 4.

- [ ] **Step 6: Inverter a dependência — `blog-meta.ts` deixa de importar `blog-posts.ts`**

Como o objetivo final é que `BlogPreview`/`/blog`/`sitemap.ts` **não** puxem as 67 KB de `content`, gerar `blog-meta.ts` como dado estático próprio (copiando os mesmos objetos, sem o campo `content`) em vez de derivar via `.map()`:

Reescrever `src/data/blog-meta.ts` copiando cada objeto de `blogPosts` em `blog-posts.ts`, removendo apenas a chave `content` de cada um, mantendo a mesma ordem e valores. (Executar com um script Node local que lê `blog-posts.ts` e serializa os campos sem `content`, para evitar erro de transcrição manual em ~15+ posts.)

Exemplo de script auxiliar (rodar uma vez, não faz parte do bundle):

```js
// scratch script, rodar com: node -e "..."
const { blogPosts } = require('./src/data/blog-posts.ts'); // ajustar para ts-node ou compilar antes
```

Como o projeto não tem `ts-node` configurado, a abordagem mais simples e confiável é manter `blog-meta.ts` como está no Step 2 (`.map()` sobre `blogPosts`) **e** confirmar via bundle analyzer (Step 7) que o tree-shaking do Next já remove o `content` não referenciado nos client bundles de `BlogPreview`/`/blog`. Next 15 com Server Components faz isso automaticamente quando o componente consumidor é Server Component — então este step só é necessário se o Step 7 mostrar que o `content` ainda está entrando no bundle do cliente.

Se `content` ainda aparecer no chunk client, voltar ao Step 6 e materializar `blog-meta.ts` como array literal sem `content` (copiado manualmente dos metadados, sem o HTML).
